## 1. 问题与目标

本次安装版检查覆盖会话入口、只读委派配置、专家配置与启动条件，没有重新启动模型任务。竞品研究来自官方文档，未登录各竞品逐一实测。

当前问题：

- “对比”与“多 AI 协作”分散，前者同题多答，后者分工与互审，入口没有解释用途。
- 弹窗要求重新输入目标，再选择执行者、独立审查者，缺少启动前的分工预览。
- 专家页同时展示七类角色、Skills、AI“后端”、模型、回合预算和能力确认；默认团队固定为前端、Java、测试。
- 配置、运行记录、任务操作和结果都在一个长弹窗中，查看进度时会打断主会话。
- 启动条件分散在表单各处，禁用按钮附近没有统一说明下一步需要补什么。

目标：用户在当前会话描述任务，查看并调整分工，明确启动；运行过程持续可见；结果先呈现建议、证据和需要用户处理的事项。模型、Skills 和预算仍可检查和调整，但按需展开。

用户故事：

- 在 Codex 会话中说“让 Claude 调研登录刷新问题，再独立审查”，查看计划后执行，最后仍在原 Codex 会话看汇总。
- 在 iOS 项目中说“评估首页改版”，先得到相关专家建议，调整团队后启动独立研究和互审。
- 在代码任务中查看允许修改的文件和验证计划，启动隔离执行，审查通过后逐项预览和采纳。
- 离开当前会话后回来，能看到执行到哪一步、是否需要处理；重启后查看历史，不自动执行。

## 2. 产品依据与采用范围

| 参考产品 | 官方可核实行为 | 本次采用的交互原则 |
| --- | --- | --- |
| [Claude Research](https://support.claude.com/en/articles/11088861-use-research-on-claude)及[多 Agent 工程说明](https://www.anthropic.com/engineering/multi-agent-research-system) | 从输入区启用研究；主持者分派独立研究并汇总带引用的结果 | 目标优先、主持者提议分工、证据可查看；内部多 Agent 不代表跨品牌协议 |
| [Gemini Deep Research](https://support.google.com/gemini/answer/15719111?hl=en) | 输入问题后生成可编辑计划；确认开始；等待时可离开；最终打开报告 | 计划可修改、执行与计划分离、结果可回访；不据此推断有专家互审 |
| [Cursor Agents](https://cursor.com/changelog/3-0)及[多 Agent 评选](https://cursor.com/changelog/2-2) | 多任务并行、隔离环境、并排会话；同题多模型结果可评选 | 持续任务导航、结果比较；不混淆同题对比与职责分工 |
| [Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams) | 自然语言安排职责，成员沟通、质疑发现，主持者汇总；仍为实验功能 | 角色职责明确、展示分歧及依据；不把终端内部团队当成现成跨 CLI 方案 |
| [ChatGPT Work](https://learn.chatgpt.com/docs/use-chatgpt#what-chatgpt-work-can-do) | 围绕任务规划、工具、委派和可查看结果组织工作 | 保留主要会话入口，围绕目标、进度与交付组织协作 |

以下布局、专家推荐和分工卡片是 HCode 的设计选择，尚未通过可用性验收。沿用现有组件、字体和设计语言；采用 Apple Design 的信息层级、即时反馈、空间一致性、可中断反馈及无障碍原则。

## 3. 一个输入区，四种工作方式

输入区统一显示“工作方式”选择，默认“普通对话”。AI 品牌、权限模式和模型设置继续保留自己的含义。

| 工作方式 | 用户意图 | 是否自动交换结果 | 最终产物 |
| --- | --- | --- | --- |
| 普通对话 | 与当前 AI 完成任务 | 沿用普通会话行为 | 当前 AI 的回复与产物 |
| 协作执行 | 当前 AI 委派，其他 AI 执行，独立审查并有界修订 | 是，由现有调度器编排 | 主持汇总、报告或代码候选、验证和审查记录 |
| 专家评审 | 多个角色独立研究、相关角色互审、当前 AI 汇总 | 是，按固定研究与互审阶段 | 共识、分歧、证据、未验证事项和建议 |
| 多模型对比 | 多个 AI 回答同一个问题 | 否，保留现有 `startCompare` 行为 | 并排答案，由用户比较 |

“专家评审”是原“专家独立研究与互审”的界面名称；引擎模式仍为 `experts`。菜单中用一句话解释各方式，不要求用户先理解 Provider、CLI、原生线程或 MCP。

选择工作方式不发送消息、不创建运行。沿用已有输入文字和附件草稿，用户不用在另一弹窗重输目标；切换会话后草稿按会话保存。附件是否能进入协作上下文逐类验证，不支持的附件明确提示并阻止启动，不能静默忽略。

当前会话的 AI 自动担任主持者，界面显示“由当前 Codex / Claude 会话主持”，不额外选择主 AI。发起能力、目标执行能力和任务权限分别检查；尚未准入的 agy 发起、StepCode/pi 协作仍说明原因。任何新会话建议都须由用户显式选择，不能自动换线程或品牌。

## 4. 协作执行路径

```text
当前会话填写目标 → 查看协作计划 → 调整分工与范围 → 开始协作
→ 执行 → 必需验证 → 独立审查 → 按阻塞意见修订 / 复审
→ 原会话汇总 → 查看报告 / 预览代码 → 用户采纳代码候选
```

### 4.1 查看计划

选择“协作执行”后，发送按钮显示“生成协作计划”。点击后在原会话关联一个计划草案，右侧打开计划面板；原输入在草案落盘成功后才标为已提交，失败时文字与附件保留。

当前 AI 提议分工。计划必须结构化且经过主进程校验，界面展示：

- 目标与预期产物：只读报告或隔离代码候选。
- 资料范围：项目、选定文件/引用、已验证可用的附件；明确当前上下文边界。
- 每个任务：简短名称、职责、执行 AI、允许的文件范围和验收要求。
- 独立审查：默认建议使用主持 AI 的配置，实际为新审查会话，写明“Codex 独立审查”等名称。
- 运行限制：并发、修订、预算及实际能力；代码任务展示隔离范围、复制清单和验证计划。
- 尚缺条件：逐项说明缺少模型、允许路径、验证项、有效角色组合或会话能力。

用户可直接修改文本字段、选择 AI、删改任务，也可说“只保留登录模块”“让 Claude 实现、Codex 审查”生成新计划版本。修改使旧确认失效；草案错误与缺少条件显示在相关字段和主操作附近。手动编辑是一条明确可选路径，规划失败不得伪造 AI 建议。

### 4.2 明确开始与运行

主操作为“开始协作”；代码任务使用“确认范围并开始代码协作”。即使普通会话处于完全放行，生成计划也不等于授权启动协作。

主进程启动时重新检查当前会话身份、忙碌状态、模型、预算、上下文、Role/Skill 版本及代码清单。条件变化时列出需重新确认的差异，不自动扩大权限、不替换模型。

运行后输入区保留一条简短状态：“2 项任务 · 独立审查中”“需要补充资料”等，点击打开任务面板。代码候选通过审查仍显示“待采纳”；采纳后显示“已采纳”，需要组合复测的事项继续可见。

代码执行保留当前单任务或固定两个独立写任务范围。计划不可把两个任务写成未经支持的依赖链；主进程发现顺序依赖、交叉写入或不支持项目准入时阻止启动并说明。只读协作继续遵循现有交付数量与任务工具限制。

## 5. 专家评审路径

```text
描述问题 → 查看推荐专家与各自研究任务 → 调整团队与资料范围
→ 开始专家评审 → 独立研究 → 相关角色互审 → 当前原会话汇总
→ 查看共识、分歧、证据与建议 → 补资料并选择具体阶段继续
```

### 5.1 推荐团队

保留七类专家与已经确定的本机 Role/Skill 组合：

| 专家 | 职责与组合保留规则 |
| --- | --- |
| iOS | iOS 语言/平台角色、移动端角色、Apple Design 及现有组合 Skills |
| 安卓 | 安卓语言/平台角色、移动端角色、Apple Design 及现有组合 Skills |
| 前端 | 前端角色、Apple Design 及现有组合 Skills |
| Java 服务端 | Java、Spring Boot、架构师及现有组合 Skills |
| 需求调研 | 需求与业务分析角色及现有组合 Skills |
| UI 设计 | UI/UX 设计角色、Apple Design 及现有组合 Skills |
| 测试 | 测试与质量角色及现有组合 Skills |

推荐依据为用户目标、选定上下文及有证据的项目特征，不能只凭目录名称猜平台。专家先由主持 AI 推荐，HCode 校验是否属于七类、组合是否可加载、模型是否可用、预算是否足够。最少 2 位，最多 7 位；默认不启动全部专家。

例子：iOS 首页改版先推荐 iOS、UI 设计、测试；涉及服务契约时再建议 Java。单纯前端表单问题先推荐前端、测试；涉及需求歧义时建议需求调研。无法确定项目时展示原因，用户选择团队，不静默沿用固定前端/Java/测试三人组合。

每位专家默认只展示“角色、此次负责的问题、执行 AI”。“模型”和“组合角色与 Skills”在详情中查看。专家不永久绑定品牌；AI 的选择使用用户已有配置及已验证能力，Gemini 继续要求选择账号可用模型，不自动代选或降级。相同模型不同角色显示为不同视角，不称为独立模型证据。

### 5.2 能力说明与启动

主界面直接说明“仅分析项目文件；不联网，不执行测试或设备验证”。可展开“实际能力与缺少工具”查看本机组合、冻结版本及未执行步骤。

能力确认改为针对本次选定组合的简短说明和确认，不要求用户读懂“指令加载”等实现术语。现有 `acceptProfileLimitations` 语义保留；只有用户查看并明确接受本次限制才记录确认，不能自动勾选。选定组合、版本或能力范围变化使确认失效。

回合预算放到高级设置；计划仍展示基础回合需求与上限，超出预算时提示调整团队或预算。隐藏预算输入不会取消预算约束。

### 5.3 专家结果

结果默认按以下顺序展开：

1. 当前 AI 的总体建议。
2. 经互审支持的共识；附结论对应的来源。
3. 未解决分歧：各方主张、证据与互审评价。
4. 证据不足、未执行验证及缺席专家。
5. 用户可以处理的下一步：补资料、选择专家重新研究或重新互审。

来源跳转必须关联真实 `expertId/versionId/claimId` 及冻结报告。不能把相似结论、多数赞同或 AI 的总结转成新的“已核实”状态。

本轮继续使用独立研究、相关角色互审、当前会话汇总。无限讨论、全互审和专家回应修订不进入本次范围；自然语言“继续评审”必须转成明确的目标专家和阶段，显示待执行动作后由用户开始。

## 6. 任务面板、消息和状态

复用会话侧面板体系，增加“协作”面板类型。任务列表、当前阶段、待处理项和结果常驻面板；日志、原生会话、Token 及配置放入详情。主会话继续承担目标、主持解释和汇总。

- 规划时打开计划；用户开始后切换为进度；完成后结果优先。关闭面板只改变展示，不停止运行。
- 文件、差异和协作面板共用导航，点击证据后可返回原任务，保留选择和滚动位置。
- 切换会话时面板绑定对应 `sessionKey/nativeSessionId`，不会把其他项目的 Run 显示到当前会话。
- 工作会话保留可访问历史，并标明所属协作、任务与角色，默认在协作下分组，避免内部长提示词充当主要会话标题；历史识别方式在 U0 验证。
- 运行期间主持会话的普通发送保持现有占用约束，输入区说明“正在协调协作”。补资料从协作的明确入口提交；回复不能错误发给普通聊天或另一个任务。
- 需要用户决定时列出问题、影响范围和回复操作；暂不新增“随意联系任意专家”的消息协议。

| 真实状态 | 默认界面表达 | 可执行动作 |
| --- | --- | --- |
| 草案生成中 | 正在生成计划 | 取消规划；保留草稿 |
| 待确认草案 | 计划待确认 | 编辑、查看能力、开始、放弃草案 |
| 执行 / 研究 / 验证 / 审查 / 修订 | 明确阶段和当前任务 | 查看详情、补资料、暂停接管、停止 |
| `awaitingUser` | 需要你处理，并列原因 | 回复或选择明确续跑动作 |
| `stopping` | 正在请求停止，等待确认 | 查看原因；不提前开放接管 |
| `paused` | 已暂停 | 查看、人工接管、确认后继续 |
| 交付 `accepted` | 审查通过；代码另显示待采纳 | 查看报告、预览、冲突检查与采纳 |
| Run `completed` | 已汇总 | 查看结果、明确选择重新执行/复审 |
| 失败 / 中断 / 取消 | 具体原因与保留产物 | 依据现有能力提供恢复；不默认重试 |
| 采纳冲突 / 未完成恢复 | 原项目需要处理 | 查看差异或先恢复；禁止新续跑绕过锁定 |

键盘可访问所有入口、字段和任务；关闭面板后焦点返回触发控件。状态不能只靠颜色；错误可被辅助功能读取。长内容可滚动，缩放时主操作可到达；不自动抢焦点或把用户滚动位置拉回底部。使用现有设计 Token，动画可中断并尊重减少动态效果设置，不新增装饰性依赖。

## 7. 实施决策与模块边界

### 7.1 草案不等于 Run

当前 `CollaborationService.start/startExperts` 会直接占用源会话、启动 Runner；代码初始化还会建立隔离工作区。不能用这些方法生成预览计划。

新增独立的草案契约：`draftId`、版本、绑定的会话/项目身份、模式、目标、上下文引用、分工/专家、模型选择、权限与验证要求、能力快照、缺少条件、预算使用及对应规划回合。U0 已实现单项只读子集及 `editing/preparing/ready/blocked/cancelled/abandoned/starting/started` 状态；其余模式字段由对应切片扩展，不扩展执行 Run 的终态语义。

U0 验证以下准入约束：

- 规划读取必要上下文和提交结构化草案；HCode 协作入口不创建 worker、执行代码、建立写副本或采纳候选。
- 同一当前原生会话完成规划和后续主持；已存在普通线程无法补工具时明确阻止，不新建替代线程。
- 规划期间不授权新增网络、写入或 CLI 工具。普通会话已有权限仍存在，应用侧拒绝协作启动不等于全会话只读沙箱；Provider 若无法可靠限制该规划回合的执行行为，不开放 AI 自动规划，明确提供手动填写计划的路径。
- 每次规划尝试和格式修正记录真实回合及用量，确认启动后计入同一协作预算；不能把前置规划变成预算外的无限调用。U0 核对现有专家基础回合计算及 Runner 是否可复用规划结果，避免重复规划。
- 用户开始时提交 `draftId/revision`，主进程重新校验并以幂等操作创建唯一 Run。开始成功后草案绑定 Run；快速双击、旧版本确认、并发窗口和响应丢失不能产生两个运行。
- UI 编辑不直接修改已执行快照；启动后使用现有消息和显式续跑，权限或目标扩大需新计划和确认。
- 草案重启后只展示待确认或被中断的规划状态；持久化失败明确阻止启动。旧 Run 继续按原模型加载，不能为展示新界面伪造历史草案。

接口名、存储版本及规划工具桥接由 U0 验证后确定；本计划不提前声称现有 IPC 或 Provider 已支持这些能力。

### 7.2 职责分层

| 业务边界 | 当前入口 / 模块 | 本次职责 |
| --- | --- | --- |
| 输入与工作方式 | `composer/Composer.tsx`、草稿模块、`ConversationView.tsx` | 复用输入上下文、方式选择、发送语义；不在 Composer 实现规划/调度 |
| 草案规划 | 新增协作草案 Service、Policy、Repository 与共享契约 | Service 编排规划与确认，Policy 管准入/版本/预算，Repository 管持久化；按实际职责落文件 |
| 执行生命周期 | `CollaborationService/Runner/Repository`、`SessionExecutionService` | 只接收已确认有效计划；沿用原生终态、占用与恢复规则 |
| 协作视图 | `collaboration/CollaborationPanel.tsx` 及现有 Run/Expert 组件 | 旧入口渐进迁移；拆分工作方式入口、草案视图、进度、结果，不继续增加万能弹窗 |
| 专家组合与能力 | `ExpertSetup/useExpertProfiles`、ExpertProfile 服务、能力快照 | 提议/调整团队、实际能力详情、冻结与确认；不修改本机角色/Skills |
| 侧面板与导航 | `conversation/SidePanel.tsx`、`uiStore.ts` | 共用容器与面板路由；UI 只保存选择、展开、滚动等状态 |
| 对比 | `CompareView`、`startCompare` | 入口说明与迁移，保留并排同题对比行为，不加入协作调度 |
| 代码候选 | 现有 Workspace/Validation/Adoption 模块 | 重用准确范围、检查计划、冻结版本、冲突与恢复；UI 不判定可以写回 |

主进程拥有草案版本、Run、预算、权限、采纳与业务错误；渲染进程拥有未保存输入和局部展示。报告和会话来自真实持久化，不从界面标题、品牌图标或提示词推断任务成功。

## 8. 改造计划：U0–U6

执行顺序：`U0 → U1 → U2 → U3 → U4 → U5 → U6`。每个切片交付一条可运行用户路径，包含其必要 UI、协议、规则与验证。U0、U1 验收已完成，U2–U6 待实施；工期结合已验证的原生草案能力和各切片范围再估算。

### U0 — 验证当前会话的计划草案与启动隔离

**Type — AFK；真实原生限制和方案取舍验收 HITL。**

**What to build**：打通一条 Claude/Codex 原会话“生成结构化只读任务计划 → 用户修改 → 确认启动唯一 Run”的最小路径；验证草案持久化、幂等、预算、原生身份及规划行为限制，不扩展任务种类。

**Acceptance criteria**

- [x] 生成、编辑、取消计划均不创建执行者、工作区或修改原项目；规划回合失败不显示有效计划。
- [x] 当前原生会话身份保持；Claude/Codex 真实规划及原会话恢复通过，缺工具历史线程被准入拒绝，无法限定规划行为的组合不开放。
- [x] 旧版本、双击、并发确认、预算不足及持久化失败不能开始错误 Run；响应丢失后能取回同一个 Run。
- [x] 规划尝试计入预算，启动后不重复规划；重启不自动规划或执行。格式无效明确失败，本轮未开启自动修复，由用户显式重新生成。
- [x] 形成准入记录：只接收入口文字与实际工具读取的项目文件；普通聊天附件不带入；原生身份可找回草案，旧 Run 可读；行为测试、`pnpm typecheck`、`pnpm build` 及真实双向 CLI 最小验收通过。

**Boundaries**：Domain 为协作草案与启动；Entry points 为草案接口/最小计划视图；State owner 为主进程草案服务；IO owner 为草案 Repository 和 SessionExecutionService；Not in scope 为新执行框架、品牌替换、代码采纳、全量 UI 重构。

## 9. 验证策略与完成标准

高风险规则采用行为先行的红绿验证：草案不能执行、会话身份不变、确认版本/幂等、预算计数、角色/能力变更、双任务范围与冲突、停止确认、精确续跑及重启兼容。允许模拟外部 CLI、网络与文件系统故障，不能模拟掉准入和编排业务规则。

UI 验证通过用户公开路径检查模式切换、输入保留、计划编辑、禁用原因、任务导航、证据跳转和恢复；不以私有函数、DOM 文件结构或截图存在代替功能验收。实际布局在现有界面上先验证，再按设计细节验收。

每个 U 切片须有独立实施记录，区分已实现、自动测试、真实原生调用、桌面操作与未覆盖范围。首版现有能力仍按 S 系列记录判断；U6 通过前不能宣称交互改造完成。

## 10. 不在本次范围与剩余决策

不新增多 Agent 框架、工作流画布、任意专家私聊、递归委派、无限互审、自动代码采纳或提交推送。Gemini 写入、agy 自主发起、移动/Java 实际构建、真机和插件工具继续另行准入。

U0 的真实决策点为：各 Provider 能否在原生当前会话中可靠生成受限草案，如何复用已有规划回合并保持累计预算，以及内部会话身份如何在重启后归组。不能通过静默换品牌、线程或默认成功绕过这些决策。

用户已确认目标优先、主持提议分工及高级配置的方向。本次默认所有协作与专家计划都需明确点击开始；日后若要只读计划自动启动，需单独确定产品与权限规则。本次不为视觉样式另设未经验证的全新设计系统。
